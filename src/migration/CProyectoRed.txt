PROPÓSITO
---------
Modelo de dominio "Proyecto de Red" para los sellos de planos GIS (PNI).
Encapsula la lectura del active_scheme de Smallworld y agrega información
de 3 bases de datos para mostrarla en los sellos de plano:

  · :design_admin :swg_dsn_scheme       → collScheme   (datos del diseño)
  · :design_admin :swg_dsn_project      → collProyecto (datos del proyecto)
  · :catalogos    :user!_cat_nodos_cm   → collCentral  (datos de la central)
  · :landbase     :user!_distrito       → oDto (vía CDistritoE)
  · :design_admin :user!_plano          → oPlano (lazy)

Expone +30 getters string que devuelven el campo correspondiente del record
o sValor_Defecto ('') cuando no hay scheme activo (prvValida_proyecto() falla).

TIPOS DEFINIDOS (D5 — XxxRecord para campos user!_*)
------------------------------------------------------
SchemeRecord
  Campos `user!_*` del registro :swg_dsn_scheme (colonia, calles, cp,
  distrito, numero_ruta, dtos_afectados, refs, aprobo). + id +
  swg_dsn_project_id (FK al proyecto padre).

ProjectRecord
  Campos `user!_*` del registro :swg_dsn_project (direccion_divisional,
  responsable, supervisor, programa, oficinas, fechas, …). + name + id.
  `user!_central` es un sub-objeto CentralCatRecord (puede ser undefined).

CentralCatRecord
  { 'user!_siglas', 'user!_central', 'user!_nom_nodo' }
  Registro :user!_cat_nodos_cm en :catalogos.

PlanoRecord
  { id, 'user!_nombre', 'user!_tipo', 'user!_observ' }
  Versión simplificada del :user!_plano de :design_admin.

ActiveSchemeRef
  Stub mínimo de swg_dsn_admin_engine.active_scheme — { id }.

MockProyectoDB
  Contenedor con las 3 BDs Smallworld + el active_scheme + landbase
  para el CDistritoE anidado.

CentralLite / PlanoLite / CTramoFoE
  Stubs ligeros para Central(), Plano(id) y obten_tramo() — sin
  acoplar a las clases hermanas todavía sin migrar.

DIFERENCIAS RESPECTO AL MAGIK ORIGINAL
----------------------------------------
· Las 3 BDs (design_admin / catalogos / landbase) no existen en navegador.
  Se modela un MockProyectoDB inyectable por constructor.

· `swg_dsn_admin_engine.active_scheme` se simula con
  MockProyectoDB.active_scheme — un ActiveSchemeRef { id } o undefined.

· `collProyecto.field(:user!_xxx) <> _unset` se traduce al chequeo
  `rec[key] !== undefined`. El Magik distingue "campo no existe en
  schema" vs "campo unset"; en TS se colapsa a undefined.

· Los `write("Se tomó el número de ruta …")` del Magik se omiten —
  son trazas de consola sin valor en migración.

· Los métodos pep / oei / oe / opb se conservan devolviendo el valor
  por defecto en ambas ramas (el código original que accedía a
  collScheme.user!_operacion / _oei / _oe está comentado desde
  el 25/05/05).

· Bug preservado: `reviso()` devuelve el campo `user!_aprobo` (igual
  que en el Magik) — no es typo de la migración.

· mes_anio: las posiciones .subseq(4,2) → mes y .subseq(9,2) → año
  asumen formato exacto "dd/mm/yyyy". Si llega "dd/mm/yy" o similar,
  el resultado es incorrecto (mismo comportamiento que el Magik).

· obten_tramo: se omiten los write() de traza pero la lógica de
  recálculo (`cveRuta || cveTramo distintos del actual`) es idéntica.

· Central() y Plano() devuelven stubs ligeros (CentralLite / PlanoLite)
  en lugar de instanciar c_central_e / c_plano_e — esas clases no
  están migradas en el showcase actual y crear acoplamiento sería
  prematuro. Las interfaces ligeras exponen las propiedades que el
  Magik consumiría.

· La UI añade:
  · Selector de active_scheme (3 valores: 1001 / 1002 / unset)
  · Pill prvValida_proyecto / existe?
  · 3 tarjetas con los +30 getters agrupados (PROYECTO / SCHEME / Distrito)
  · Controles para obten_tramo (cveTramo + cveRuta opcional)
  · Selector de Plano(id) y test de Central()
  · Probador de mes_anio con varios presets incluyendo uno inválido
    para visualizar el throw new Error
  · Resaltado naranja sobre los valores que son fallback "_XYZ_" para
    distinguirlos del dato real
